# 虚拟乌托邦 BP4 开发排期与风险评估

> 版本：BP4-ROADMAP-DRAFT-1.0  
> 预计周期：8至10周  
> 依赖：BP3最终交付包、Phase5身份服务、生产环境资源

## 1. 排期假设

- 团队配置：1名技术负责人、1名后端、1名前端、1名实时通信工程、1名测试、1名运维。
- 开发按周迭代，每周至少一次回归。
- PostgreSQL、Redis、TURN、监控平台可申请。
- 语音继续采用mediasoup或迁移至等效SFU。

## 2. 里程碑

| 里程碑            | 周期     | 范围                                    | 出口条件                 |
| ----------------- | -------- | --------------------------------------- | ------------------------ |
| BP4-M1 平台基础   | 第1-2周  | PostgreSQL迁移、Schema、迁移校验        | 冻结数据可完整迁移和回滚 |
| BP4-M2 实时通道   | 第3-4周  | WebSocket、presence、聊天、Avatar、事件 | 100连接和断线续传通过    |
| BP4-M3 语音生产化 | 第5-6周  | SFU多Worker、TURN、节点健康检查         | 公网与移动网络语音通过   |
| BP4-M4 安全运维   | 第7周    | 限流、幂等、审计、监控、告警、备份      | 安全与恢复演练通过       |
| BP4-M5 运营增强   | 第8周    | 运营后台、模板、数据看板                | P1核心流程通过           |

## 5. 风险清单

| 风险                       | 概率 | 影响 | 缓解措施                         | 触发信号            |
| -------------------------- | ---- | ---- | -------------------------------- | ------------------- |
| 数据迁移丢失或错位         | 中   | 高   | 双读校验、快照回滚、业务抽样     | 迁移前后数量不一致  |
| SQLite与PostgreSQL行为差异 | 中   | 高   | 契约测试、迁移适配层、事务对比   | 并发或时间字段异常  |
| WebSocket风暴              | 中   | 高   | 限流、批量合并、背压、分频道订阅 | 连接或消息量突增    |
| 重连重复写入               | 中   | 高   | 幂等键、事件序号、写操作去重     | 奖励或库存重复      |
| mediasoup节点故障          | 中   | 高   | 多Worker、健康检查和房间迁移     | 节点CPU或丢包异常   |
| TURN不可用                 | 低   | 高   | 多TURN、端口监控和回退节点       | 移动网络连接失败    |
| 监控指标缺失               | 中   | 中   | 建立最小指标集和告警门槛         | 异常无法定位        |
| 迁移窗口超时               | 中   | 高   | 预演、分批迁移和回滚脚本         | 迁移超过计划时间    |
| 运营后台权限过大           | 中   | 高   | 四眼审核、审计、最小权限         | 非管理员调用管理API |
| BP3兼容回归                | 低   | 高   | 固定回归集、版本隔离和自动测试   | 旧接口或旧数据异常  |

## 6. 回滚策略

### 数据库

- 迁移前保留SQLite和PostgreSQL双快照。
- 迁移失败回到SQLite只读模式。
- 数据校验失败不切换主写入。

### 实时通道

- WebSocket故障时保留BP3轮询作为降级路径。
- 只影响实时体验，不阻断任务、背包和权限读取。

### 语音

- 单节点故障时将新连接分配到健康节点。
- TURN故障时显示明确状态并允许文字聊天降级。

## 7. 验收Gate

### Gate A：迁移

- 迁移可重复执行。
- 数据数量、哈希和业务抽样一致。
- 回滚在30分钟内完成。

### Gate B：实时

- 100并发连接稳定。
- 断线5秒内恢复。
- 重连不重复写库存和奖励。

### Gate C：语音

- 公网、移动网络和NAT环境可连接。
- 单Worker故障不影响全站。

### Gate D：安全运维

- 限流、审计、告警、备份和恢复全部演练通过。

### Gate E：整体

- BP3冻结回归通过。
- BP4 P0/P1 E2E通过。
- 压测和故障演练通过。

## 8. 上线策略

1. 先部署staging，导入冻结数据。
2. 进行双读和只读流量验证。
3. 切换实时通道和语音节点。
4. 开放管理员和运营账号。
5. 按用户百分比灰度。
6. 观察24小时后再切换全量写入。

## 9. 成本与资源

需要评估：

- PostgreSQL和Redis托管成本。
- TURN带宽成本。
- SFU节点CPU和网络成本。
- 日志、指标和备份存储成本。
- 多环境资源成本。

## 10. 主要决策点

1. PostgreSQL托管还是自建。
2. Redis是否作为presence和实时路由必需组件。
3. mediasoup继续自建还是迁移LiveKit。
4. 实时事件保留时长和回放范围。
5. 运营后台是否独立部署和独立域名。
